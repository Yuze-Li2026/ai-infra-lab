# DBDB：从内存树到持久化数据库

原作者 **Taavi Burns**。先阅读 [DBDB 原章](https://aosabook.org/en/500L/dbdb-dog-bed-database.html)。代码固定为 aosabook/500lines 提交 `fba689d101eb5600f5c8f4d7fd79912498e950e2`；MIT 代码和许可原文位于 `labs/dbdb/upstream`，书籍正文未复制。

## Learn：先掌握机制

先修 Python 抽象、递归、二叉搜索树、文件位置、锁与提交。阅读原章的数据结构、物理存储与逻辑接口说明，画出“键 → 树节点 → 文件地址 → 根地址”的关系。解释：修改尚未提交时关闭连接，为什么不应该出现新的持久状态？为什么文件锁不能等同于数据库事务隔离？

## Design / Build：独立实现

先写接口与不变量：查找、插入、删除、长度、提交、关闭；不存在的键必须如何处理？读到磁盘节点时如何恢复对象？在自己的目录实现 `dbdb` 包，不能以复制参考包作为完成。保留设计文档、测试和提交历史。

提交目录结构应包含 `dbdb/__init__.py`、`binary_tree.py`、`logical.py`、`physical.py`、`tool.py`，并与原测试接口一致。允许采用不同内部设计，但应解释与原作者设计的差异。

## Test：使用原断言

先按[环境准备](getting-started.md)创建独立 Python 环境并安装小型 CPU 依赖。从项目根目录运行：

```sh
node scripts/lab.mjs dbdb
node scripts/lab.mjs dbdb --submission ./my-dbdb --output artifacts/my-dbdb.json
```

第一条复现参考实现，第二条检查独立包。运行器复制提交包到自己的临时目录，不修改你的源码。原断言覆盖树操作、不存在的键、持久化、CLI 及物理存储，共 **21 项**。自行增加重复提交、异常退出前未提交状态、空值、不同插入顺序等边界案例，并说明未覆盖的故障。

在“工程实验”导入 `artifacts/my-dbdb.json`。参考模式不会计入阶段个人作品。代码按本机用户权限执行，使用自己信任的代码。

## Optimize：有边界的测量

通过后自动测量 500 个随机顺序键，固定种子 37；插入、提交和关闭包含在写入计时中。另测关闭重开后的 500 次读取，并逐一检查值。一次预热、七次样本，报告中保留全部样本、中位数和文件字节数。Windows 页缓存和锁成本会影响结果；这不是断电耐久性、并发吞吐或工业数据库评测。

在相同协议下比较自己的布局、序列化或缓存改动。报告正确性是否保持、时间与空间变化、失败的优化尝试；不能只提交最快一次计时。

## Explain：复核与兼容说明

原项目依赖旧 nose 和 portalocker。Python 3.12 运行器将 nose 的两个断言别名映射到 unittest，保留 setup/teardown；CLI 明确使用当前解释器并解码参数；Windows 使用 portalocker 4.4.0 的 Win32Locker 和零偏移兼容。物理测试在 Windows 通过同一文件句柄读取夹具，断言保持不变，持久化仍由关闭重开测试验证。

逐项解释这些适配改变了什么、没有证明什么。此项目是教学数据库，不具有完整隔离、压缩或断电恢复保证。阶段验收需包含设计、独立代码、原测试、额外边界案例、测量协议和原理解释。
