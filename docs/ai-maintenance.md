# 把维护交给 AI

适用于能读取本仓库、修改文件和运行命令的 AI 开发工具。学习者只需描述想学什么、哪里不顺手或希望增加什么；维护者负责实现和验证。网站浏览本身不依赖 AI 服务，本项目也没有后台常驻机器人或自动付费服务。

## 提出一个想法

可以直接把下面这段话和自己的想法一起交给 AI：

```text
先读仓库根目录的 AGENTS.md，按现有架构完成下面的改进。
我负责学习，你负责调研、实现、文档、测试和已有授权范围内的发布。
保持中文友好、界面优雅、操作简单，不降低知识深度和验收标准。
不要把常规维护步骤交给我；确需费用、账号或设备权限时，给出具体选择。
完成后说明实际变化、验证证据、网站是否已更新，以及仍未完成的部分。

我的想法：
```

无须先理解框架、文件名和命令。例如，“我不知道读完这一节该练什么”“希望增加推理部署方向”“手机上表格不好读”都足以开始调查。AI 应从现有课程、代码和日志补齐信息；确实影响学习目标的选择再询问。

## AI 接手时做什么

1. 阅读 `AGENTS.md` 和交付清单，检查已有修改与当前分支，避免覆盖未完成工作。
2. 运行下面的离线状态命令，确认源码、目录规模和本地验证报告的对应关系。
3. 找到受影响模块与原始依据，说明可检查的结果，完成实现和必要文档。
4. 运行针对性检查及项目规定的完整检查；界面变更要实际查看桌面、手机和放大文字的截图。
5. 在已有授权和验收条件内同步仓库、发布并复核网站，留下下一次能接续的记录。

在源码根目录使用 Node 22+：

```sh
npm run maintenance:status
```

这条命令只读本地文件和 Git 元数据，不联网、安装依赖、修改学习记录或发布网站；没有 npm 维护依赖也能运行。输出包含当前分支/提交、工作区是否有修改、源码指纹、目录规模和最近的测试/浏览器报告。缺失、损坏、旧源码或未绑定来源的报告分别标明，不能只读其中的 `passed`。

`npm run check` 和 `npm run test:browser` 的报告记录运行前后的源码指纹。源码在检查期间变化时，检查返回失败；后续源码变化会让离线状态把旧报告标为过期。指纹用于防止误用旧结果，不是数字签名，也不证明教学正确性、硬件覆盖或远程发布。

Git 不可用或源码来自 ZIP 时仍可读取本地状态，Git 信息标为空；损坏的报告保留原文件并给出诊断。离线命令不会查询 GitHub，所以 CI、Pages 和真实线上文件必须另行核对。

报告的 `status` 字段按以下含义读取：

| 状态 | 含义 |
| --- | --- |
| `passed` | 报告通过，运行前后源码与当前一致 |
| `failed` | 当前源码的检查失败，包括环境准备失败 |
| `stale` | 报告对应其他源码，需要复验 |
| `source-changed` | 检查期间源码发生变化，结果不能用于验收 |
| `unbound` | 历史报告未记录源码指纹，不能认定对应当前源码 |
| `missing` | 本地没有该报告 |
| `invalid` | 文件损坏、结构错误、符号链接或超过大小限制，保留原文件排查 |

源码指纹包含网站、文档、实验、维护脚本、测试、配置和仓库入口，排除产物、个人作品及安装环境。具体范围集中在 `scripts/verification-state.mjs`；新增顶层代码目录时必须同步该范围。状态命令退出 0 表示完成了清点，不表示检查通过；未知参数返回 2，源码读取失败返回非零。可使用 `node scripts/maintenance-status.mjs` 取得不含 npm 提示行的 JSON。

## 按改动选择验证

| 改动 | 维护者必须完成的工作 |
| --- | --- |
| 资源或知识节点 | 核对原作者、版本、许可与中文版本身份；同步目录、致谢、选章和覆盖矩阵；执行完整检查 |
| 排版、导航、学习记录或阅读器 | 完整检查和浏览器回归；查看桌面/手机截图、键盘操作、200% 文字及失败恢复 |
| 报告格式、阶段条件或存储 | 验证旧备份、并发、损坏数据、失败保存和恢复；参考结果不得进入独立作品验收 |
| 实验执行器或课程版本 | 固定来源与依赖；实际准备、运行、错误实现和恢复；标明 CPU、CUDA、Linux、多卡等真实条件 |
| 依赖、构建或工作流 | 复核官方变更、许可和权限；更新版本锁/哈希；运行同提交 CI、归档恢复和部署复核 |

命令、环境和回滚方法见[维护者教程](maintainer-tutorial.md)与[维护指南](maintenance.md)。工程范围见[交付清单](delivery-checklist.md)。

## 交接记录

一次维护结束时，给所有者一段简短结论，并在相应文档/提交中保存以下事实：

- 解决了什么实际问题，哪些文件或知识范围受影响。
- 执行了哪些检查，报告位置、源码提交和限制是什么；未执行的部分保持明确。
- 仓库是否同步，正式网站对应哪个提交；本地预览不能称为已经上线。
- 还剩什么、需要什么外部条件，下一位维护者应从哪里继续。

新增结论写入相关现行文档和[验证记录](verification.md)，历史结果保留版本边界。未完成项集中维护在[交付清单](delivery-checklist.md)，避免只留在聊天里。PR 使用仓库模板说明行为变化与验证；不要求学习者填写技术报告。

1.0 首版按所有者确认的核心支持范围验收。后续维护同时保留高级实验清单：逐项补实际环境与原始证据，完成一项再更新状态，不以首版发行代替全范围验收，也不让未验证的远程执行能力出现在可直接运行的入口中。

## 什么时候需要学习者参与

常规编辑、测试、文档修复和已有授权内的同步由维护者执行。只有目标无法从上下文判断、需要新的费用或大规模下载、账号验证、设备权限及超出既有授权的公开操作时，才要求学习者作决定。先给具体方案、影响和已完成的准备工作；等待期间继续不受影响的部分。

目前在线阅读、选章、进度和备份可直接使用；本地编译、GPU 与原课测试仍在相应机器运行。维护规范不会自动产生远程实验后端。今后若接入在线实验，需另行实现并实测环境隔离、数据保存、限额、费用与失败恢复，完成后再出现在学习入口。
