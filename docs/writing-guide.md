# 文档写作规范

适用于本站维护的 README、贡献与安全说明及 `docs/` 下的中文文档。第三方原文、许可证和冻结源码保持原样。维护者修改文档后，需完成格式检查、事实核对和操作验证。

## 选择文档类型

采用 [Diátaxis](https://diataxis.fr/) 的四类结构，以读者的任务决定内容：

| 类型 | 回答的问题 | 必须交代的内容 |
| --- | --- | --- |
| 入门教程 | 第一次怎样完成一件事？ | 起点、环境、连续步骤、预期结果、下一步 |
| 操作指南 | 怎样解决具体问题？ | 适用条件、操作、结果核对、失败恢复 |
| 接口参考 | 某个参数或格式是什么？ | 名称、类型、默认值、限制、返回结果、错误 |
| 设计说明 | 为什么这样实现？ | 问题、依据、选择、取舍、适用边界 |

发布记录与审查记录单独保存，标注版本和日期。历史结果不用于描述当前支持情况；操作指南不堆入开发过程、授权对话或历次测试计数。

## 文字与术语

面向执行任务的读者写作。先说明结果或要做的事，再给必要的原因。使用短句、主动语态和具体动词；一个段落说明一件事。避免空泛宣传、自我评价、机械排比和重复总结。不要用“完善了体验”代替可核对的行为，例如“保存失败时保留输入，并显示导出备份入口”。

首次出现容易混淆的术语时给中文与英文原词，后文沿用同一名称。参照[中英术语表](glossary.md)。代码标识符、命令、环境变量和文件路径用行内代码；按钮名称使用界面实际文字。中文与英文、数字之间留空格，单位写为 `8 GB`、`320 px`，版本写完整。

知识点的讲解优先复用原作者教材、成熟课程与官方文档，有可靠中文版本时优先提供。本站中文说明组织解决的问题、先修、选读范围、实践及复核标准，并补充原作之间必要的衔接；完整原理讲解以所列原作承担。公式说明符号和单位；命令沿用原接口名称，不能为翻译而改写标识符。中文导读不能冒充整部教材的授权译本，也不能把未经实测的步骤写成已验证。

不要用词汇过滤器声称判定了“人工写作”或“AI 写作”。审校关注事实是否准确、语句是否自然、读者能否完成任务。保留对风险、限制和失败行为有实际帮助的说明。

## Markdown 格式

每份文件只有一个一级标题。标题逐级使用，不跳级；标题和列表前后留空行。无序列表使用短横线，有序操作按执行顺序编号。代码围栏必须标明语言，输出使用 `text`。使用描述性链接文字，站内文件采用相对路径，外部资料使用 HTTPS。表格用于并列比较，不把多步操作塞进长表格。

规则由根目录 `.markdownlint.json` 管理。长中文段落和表格不按固定字符数硬折行，因此关闭 MD013；MD033 允许历史资料中的内联标记，页面仍经 DOMPurify 清理；MD036 允许短语加粗，但不替代标题；表格采用紧凑分隔格式。其余规则启用，不在单篇文档中添加豁免来掩盖问题。

格式检查使用 [Markdownlint](https://github.com/DavidAnson/markdownlint)，写作原则参考 [Write the Docs](https://www.writethedocs.org/guide/writing/style-guides/)。这些规范提供审校方法，不能替代技术验证。

## 命令与示例

命令前说明工作目录、工具版本和操作系统。可执行命令与预期输出分开；不得把终端提示符混入可复制命令。环境变量分别给 PowerShell 和 POSIX shell 写法。占位参数必须解释替换方法，不能把模板称为已执行案例。

命令应注明是否联网、安装依赖、修改文件或运行自己的代码。不要在普通教程中暴露维护者绝对路径、个人账号凭据或真实学习数据。失败说明给出可观察的错误、排查顺序和恢复方法，不能只写“重试”或“重装”。

验证时记录实际版本、命令、退出码、预期与实际结果。原课起始代码按预期失败只能证明执行链工作，不能证明作业完成。硬件或课程权限缺失必须记录；未执行的命令不得标为通过。

## 提交前审校

在源码目录准备维护依赖后运行：

```sh
npm ci --ignore-scripts
npm run lint-docs
npm run check-docs
```

`lint-docs` 检查格式；`check-docs` 检查文档接入、链接与标题。维护者还需逐份核对当前行为、示例、术语、适用范围和引用。格式通过不代表内容正确。修复后在站内阅读器和仓库页面检查标题、表格、代码块及手机显示。
